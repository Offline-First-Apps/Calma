# Internationalisation

**English ships alone. The architecture assumes it won't stay that way.**

Every string is externalised, every plural goes through ICU rules, every date and number is locale-formatted. Adding a language later is a translation job, not a refactor. See D-011.

---

## Stack

| Concern | Choice |
|---|---|
| Framework | `i18next` + `react-i18next` |
| Device locale | `expo-localization` |
| Plural & ordinal rules | i18next's built-in ICU plural resolution |
| Date / relative time | `Intl.DateTimeFormat` + `Intl.RelativeTimeFormat` |
| Number formatting | `Intl.NumberFormat` |
| Currency | **never formatted by us** — RevenueCat's `product.priceString` only |

### Hermes and Intl

React Native 0.86 ships Hermes with full ICU support, so `Intl` is available without a polyfill. Confirm this at boot with a smoke assertion — a silent `Intl` failure degrades to English-formatted dates in a Japanese UI, which looks broken rather than untranslated.

No `moment`, no `date-fns` locale bundles. `Intl` is already there and already correct.

## Locale resolution

```
prefs.locale === 'system'  ──▶  expo-localization.getLocales()[0].languageTag
prefs.locale === 'en'      ──▶  'en'
                                       │
                                       ▼
                            supported?  ── no ──▶  fallback chain
                                 │                 'pt-BR' → 'pt' → 'en'
                                yes
                                 │
                                 ▼
                            i18n.changeLanguage()
```

- `prefs.locale` stores either the literal string `'system'` (the default) or an explicit BCP-47 tag.
- **`'system'` is a live binding, not a snapshot.** If the person changes their phone language, Calma follows. Storing the resolved tag at first launch would silently strip that.
- Resolution runs at boot, and again on `AppState` foreground — the device language can change while the app is backgrounded.
- Region subtags degrade gracefully: `pt-BR` falls back to `pt`, then `en`. Never to a blank string.

## Where translation files live

```
packages/i18n/
├── src/
│   ├── index.ts              init, resolution, t re-export
│   ├── detect.ts             device locale → supported tag
│   ├── supported.ts          the language registry
│   └── locales/
│       └── en/
│           ├── common.json       buttons, generic actions
│           ├── onboarding.json
│           ├── breathing.json
│           ├── worry.json
│           ├── journal.json
│           ├── progress.json
│           ├── entitlement.json
│           ├── settings.json
│           └── notifications.json
```

Namespaces mirror the feature folders in `apps/native/src/features/`. A screen loads one namespace plus `common`.

This **replaces** the `apps/native/src/copy/` modules described in `systems/07-copy-and-tone.md`. The tone rules in that document are unchanged and still govern every string — the strings just live in JSON now.

### Package boundary

`packages/i18n` depends on nothing but `i18next`, `react-i18next`, and `expo-localization`. `packages/domain` must **never** import it — domain logic returns keys and data, never rendered sentences. A pure function that returns "3 days in a row" is a pure function that can't be translated.

## Key conventions

```json
{
  "worry": {
    "captured": "Got it. I'll hold onto this until {{time}}.",
    "pending_one": "You have 1 thing waiting.",
    "pending_other": "You have {{count}} things waiting."
  }
}
```

**Rules.**

- Keys are semantic, never the English text. `worry.captured`, not `worry.gotItIllHoldOnto`.
- **Named interpolation only.** Never positional, never concatenation. `"{{count}} of {{total}}"` — a translator must be free to reorder.
- **Never assemble a sentence from fragments.** `t('worry.you') + count + t('worry.waiting')` is broken in every language with grammatical gender or non-SVO order. One key, one complete sentence.
- Every count-bearing string has `_one` / `_other` at minimum. i18next resolves the correct form per locale — Arabic needs six, Polish three, Japanese one. Writing only `_other` and appending an "s" is how apps end up saying "1 things".
- Every key carries a translator comment where the context isn't obvious from the key. Tone is the product here; a translator working from a bare string will flatten it into something correct and cold.

### The tone brief travels with the strings

`packages/i18n/TRANSLATORS.md` ships alongside the locale files and contains the tone guide, the word-replacement table, and the hard rules — no exclamation marks, no diagnosis, no urgency, sentence case. A translator who hasn't read it will produce accurate strings that are wrong for this app.

## Enforcement

- ESLint flags literal JSX text inside `apps/native/src/features/`.
- A CI check fails if any locale file has keys missing relative to `en`, or keys `en` doesn't have.
- A test asserts `en` contains **zero exclamation marks** and no all-caps words — the tone audit in `plans/16` runs against the JSON, which makes it mechanical rather than manual.

## Formatting

| Thing | How |
|---|---|
| Times ("until 7:00 pm") | `Intl.DateTimeFormat` — 12h vs 24h is a locale property, never a hardcoded format |
| Dates in the journal list | `Intl.DateTimeFormat` with `weekday: 'long'` |
| "3 days ago" | `Intl.RelativeTimeFormat` |
| Counts | `Intl.NumberFormat` |
| Durations ("4 minutes") | i18next plural keys, not string maths |
| Prices | `product.priceString` from RevenueCat, untouched |

**Day and week keys are not display strings.** `dayKey()` and `weekKey()` in `packages/domain` return `YYYY-MM-DD` and `YYYY-Www` for storage and are never rendered. Anything shown to a person goes through `Intl`. Conflating the two is how a storage key ends up on screen in the wrong calendar.

## RTL

Not supported in V1, and deliberately not half-supported.

If Arabic or Hebrew is added later, the work is: `I18nManager.forceRTL` plus an app restart (RN cannot flip layout direction live — this needs a real "restart to apply" flow, which is a UX decision, not just a config flag), logical layout properties throughout, mirrored directional gestures, and a review of every screen in `plans/17-screens.md`.

Two things that are already safe: the orb is radially symmetric, and the worry-release gesture is vertical.

One thing that is not: any horizontal swipe or directional transition added before RTL exists will need revisiting.

**Don't add `writingDirection` or partial RTL handling now.** Half-mirrored layouts are worse than unmirrored ones.

## Language-neutral by design

These need no translation work, which is not an accident:

- **All seven sound effects.** A pebble, a bowl, leaves, a drum — no language, no voice. This is why the audio design works across locales for free.
- **The orb and every breathing visual.** The breath is guided by light and haptics, not words.
- **The phase label** is the one word on the session screen, and it's a single key.

The onboarding was redesigned to be visual-first partly for this reason (D-012). A 90-second voice track would have been the single largest per-language cost in the product.

## What a new language actually costs

1. Translate ~9 JSON namespaces (roughly 250–300 keys at V1 scope).
2. Read `TRANSLATORS.md` and get the tone right — this is the hard part, not the strings.
3. Verify plural forms resolve for that locale's rules.
4. Re-check every screen at 200% font scale: German compounds and Finnish run long, and the layouts must already tolerate it.
5. Add the tag to `supported.ts`.

No code changes. That's the whole point of doing this now.
